# Access policies — migration 0003

Issue #27 / PR #81 adds the database authorization boundary after the core and billing
migrations. It is not a new login screen, member app, public-site synchronization or deployment.
The coding agent and CI do not apply SQL to Supabase.

## Access model

All 17 core/money tables keep RLS and receive explicit policies. Privileges are granted separately;
having a policy does not by itself make a table or function accessible. Roles are additive:
an organiser can also be a player, and a guardian does not need an identity of their own.

| Data or action | Allowed access |
|---|---|
| Published competitions/games, venues, teams, fee schedules | Public reads; writes require appropriate admin or explicitly scoped authority. Drafts are not public. |
| Opt-in verified public roster | Only ID, display name, preferred number, positions and photo URL. No legal name, birth date, medical details or claim code. |
| Profiles, including email/phone | Own account and admin only. A scoped staff role does not unlock a member directory. |
| Private player identity | Own identity, guardian-controlled identities and admin. Verification/ownership are protected separately from ordinary profile edits. |
| Emergency/medical match contacts | A separately authorized, narrowly projected RPC for registered players of a managed match; not broad player-table access. |
| Season roster | Own request; scoped organiser/admin approval. Members cannot approve themselves or move an approved registration to another competition/player. |
| Match registration | Own/guardian-controlled registration; scoped staff check-in. Members cannot set attendance or check-in fields on insert or update. |
| Competition/game management | Limited to the granted scope. A grant in competition A provides no authority over competition B. |
| Global roles and verification | Admin only; insert-time guards also prevent self-verification. |
| Scoped grants | Admin; organisers can delegate only the explicitly supported subordinate roles within their own competition. |
| Charges, payments and financial summaries | Snapshotted payer or admin reads. Changing a guardian does not transfer access to a previous payer's financial history. |
| Financial writes and quarterly close | Admin, subject to the immutable-history rules already installed in 0002. |
| Attendance finalization | Authorized match staff/admin through a checked RPC. Internal charge writers remain inaccessible to clients. |
| Audit history and frozen summaries | Client read-only; audit visibility is admin-only because its JSON may contain private data. |

A `developer`, `treasurer` or club-wide `coach` claim is **not** an admin claim. The draft diagram's
developer column must not be read as a blanket database-data grant: no break-glass system is
implemented here. Developer accounts retain ordinary rights to their own data. Database owners
and service credentials remain privileged infrastructure, not ordinary app users.

Match-management powers are explicitly mapped to scoped `captain` and competition `organiser`
grants; a `manager`/`coach` label alone does not confer those powers. Staff edits to someone else's
match registration are limited to attendance/check-in; broader staff registration and waitlist
workflows remain later work. Admins and guardians retain their explicit registration rights.

Public queries must name supported columns rather than using `SELECT *`: anonymous game reads
exclude `notes` and `created_by`. Club contact fields and venue notes are excluded from **all client
SELECT grants**, including admin JWT sessions. Retrieving those fields needs a future admin-only
projection, not a broader public grant. The new authorization layer does not change existing static
website pages or their current data sources.

## Important security choices

- Public roster rows are projected by a dedicated read helper; the caller-security view does not
  require granting public access to private `players` rows. A public-row RLS rule combined with
  authenticated `SELECT *` would leak the private columns of opted-in members.
- Guard triggers handle column restrictions that row policies cannot express: role assignment,
  verification, identity/payer ownership, attendance and approval/scope changes.
  Date-of-birth corrections require admin authority so a known minor cannot self-remove that
  restriction. Claiming/reparenting identities needs a separately reviewed trusted workflow.
- JWT roles come only from `app_metadata.roles`, never `user_metadata` or a policy subquery into
  `profiles`. Malformed/missing roles fail closed; a role without an account is not authorization.
- Role changes are mirrored into Auth metadata, but **an existing token remains unchanged until
  refresh or expiry**. This applies to demotion as well as promotion. The future sign-in UI must
  explain/handle refresh; this migration does not implement immediate token revocation.
- The released finalization/close implementations are retained under private internal names.
  Public wrappers authorize the caller before invoking those implementations. Lock, assignment,
  promotion, charge/snapshot writers and internal lifecycle helpers are not browser RPCs.
- Definer helpers use fixed empty search paths and qualified objects. Trigger-only owner execution
  supports Auth bootstrap and trusted billing/waitlist writes; public RPC authorization does not
  trust a caller-set flag or treat a definer's `current_user` as an app admin.
- Financial snapshots and audit tables have no client write privilege, even for an admin JWT.
  Owner-written test fixtures are not an application authorization mechanism.
- Client charge inserts cannot supply the reserved `entry_id`, even with an admin JWT. The
  hosted-tournament migration must validate entries before that future workflow is authorized.

The role boundary does not complete later registration, competition-management, billing or
sign-in screens. Baseline registration checks do not replace full workflow/eligibility/deadline
acceptance tests in later issues. Do not enable real member workflows just because structural
checks pass.

## Migration order and source

0001 and 0002 were already applied in the owner's scratch project and merged in PRs #79 and #80.
Their released bytes remain unchanged. All new SQL belongs to canonical `schema.sql` section 7
and is emitted as one atomic, one-time `0003_rls.sql` migration. Do not execute the whole design
draft, rerun a released migration, or modify 0001/0002 to hide an installation problem.

```bash
python3 scripts/build_migrations.py --check
python3 scripts/check_sql.py
python3 -m unittest discover -s tests -v
```

Generation/checking now requires all three migrations. Offline checks inspect SQL structure,
policy coverage and privilege conventions, not PostgreSQL execution or full authorization.

## Manual verification reference — completed by the owner for PR #81

The owner confirmed all three RLS files before PR #81 merged and issue #27 closed. This is
owner-reported verification, not SQL execution by the coding agent. The instructions below remain
a reference for a fresh scratch project. Run them before installing demo data: the smoke scripts
intentionally require empty tables. Do not reapply a released migration.

Use the **same empty disposable Supabase scratch project where 0001 and 0002 succeeded**.
Do not use a project containing real member data. Do not rerun 0001 or 0002. Their earlier
deny-by-default smoke tests belong before 0003 and should not be rerun after policies/grants exist.

In SQL Editor select `postgres` / database owner. Run each **complete file in a separate new
query in the same project**, with no partial text selection:

1. Apply [0003_rls.sql](migrations/0003_rls.sql) **once**. Expected: no SQL errors; policies on all
   17 existing tables, with explicit grants and protected helpers. There is no new app screen.
2. Run [0003_rls_smoke.sql](tests/0003_rls_smoke.sql). Expected: no unhandled errors. Synthetic
   anonymous/member/guardian/captain/organiser/admin/developer sessions exercise the matrix,
   including denied cross-member phone/charge reads and insert-time escalation attempts.
3. Run [0003_rls_jwt_smoke.sql](tests/0003_rls_jwt_smoke.sql). Expected: no unhandled errors.
   It checks role-source restrictions, self-promotion denial, metadata synchronization, resistance
   to a spoofed temporary catalog and a simulated old-token/new-token refresh sequence.

These tests switch real database roles, but their synthetic JWT claims are set by the database
owner. They do **not** test signing, email delivery, PostgREST authentication, browser refresh or
two-session races. Owner authority to simulate claims is not available to ordinary API clients.

Both smoke scripts roll back synthetic users/data, temporary helpers and test-helper grants;
the installed migration remains. Audit sequence numbers may advance despite rollback. Each success
notice occurs before rollback and may be hidden by the dashboard. A generic no-rows result is not
sufficient if only a selection ran or any earlier statement failed.

Stop on any SQL error and report the file and exact error with private information removed.
Do not drop tables, weaken grants/policies or blindly rerun the migration. No database password
or private key needs to be shared.
